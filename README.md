# Olive Mail

### Real Email Context for Agents
You control authentication, permissions & redactions.

</div>

---

Existing mail accounts hold crucial context. But typical agents never see it – they are either thrown out of the mailboxes that hold the real work – or they get the keys to the whole kingdom.

`olive-mail` is the grown-up path in between: a local mediator that you authenticate. Agents don't handle mailbox credentials – they call `olive-mail` to search and read, so they are in the loop on all things for all their work.

Agents act as interns, not as a spokesperson for you or your company. They can't send or even draft if you don't want them to. They're still in the know, and you're still the one who speaks.

## Status

This is early. It's a working proof of concept that we already use at Nohype AI for remote bots and coding agents. But it is not the full vision yet by far.

Theoretically, a malicious agent with a shell as the same Unix user can still read the password file. Hiding that secret needs a privilege split. Constraining what a normal agent is allowed to *ask for* does not, but it is already a better interface than direct IMAP access.

`olive-mail` is still a direct wrapper around [Himalaya](https://github.com/pimalaya/himalaya). Type `olive-mail` wherever those docs say `himalaya`.

**Now.** Himalaya over IMAP. `auth` writes `~/.config/olive-mail/config.toml` plus `<email>.pass`. No SMTP block. `message send` / `smtp` / `--send` rejected. First run installs Himalaya via Homebrew if needed and puts `olive-mail` on `PATH`.

**Next.** Granular per-agent permission control: which folders, which senders, which dates; read vs draft; headers first, bodies only when asked. `olive-mail` could easily do that – it is the next work on this project, not a new architecture.

## Install

Clone this repo and run it once from the checkout (Linux and macOS):

```sh
./olive-mail auth you@example.com
```

That run will:

1. Install [Homebrew](https://brew.sh) and [Himalaya](https://github.com/pimalaya/himalaya) if they are missing (needs network; no sudo).
2. Symlink `olive-mail` to `~/.local/bin/` and, if writable, `/usr/local/bin/`. It does **not** add the repo to `PATH`.
3. Append a `~/.local/bin` snippet to existing shell rc files, and to `~/.zprofile` (macOS) or `~/.profile` (Linux) if needed.
4. Prompt for the IMAP URL (e.g. `imaps://imap.example.com:993`) and the app password. Writes `~/.config/olive-mail/config.toml` and `~/.config/olive-mail/<email>.pass` (mode `0600`).

Non-interactive:

```sh
./olive-mail auth you@example.com --imap imaps://imap.example.com:993 <<EOF
your-app-password
EOF
```

New shells pick up `PATH`. In the current one: `export PATH="$HOME/.local/bin:$PATH"` or use `/usr/local/bin/olive-mail` if that link was created.

## Usage

```sh
olive-mail mailbox list
olive-mail envelope list
olive-mail envelope search from alice after 2026-01-01
olive-mail message read 42
```

Same flags as Himalaya: [usage](https://github.com/pimalaya/himalaya#usage) · `olive-mail --help`.

If `envelope list` asks for a mailbox, set `mailbox.alias.inbox` in `~/.config/olive-mail/config.toml` to an id from `olive-mail mailbox list` (IMAP’s default is `INBOX`; some hosts use `Inbox`).

Sending is by default not allowed:

```sh
olive-mail message send …
olive-mail smtp …
olive-mail … --send
```

That is the policy gate. A shell on the same user could still bypass it — see the note in the opening.

## Layout

```
~/.config/olive-mail/config.toml     # Himalaya config, no SMTP, generated by auth
~/.config/olive-mail/<email>.pass    # app password, mode 0600
```

`config.toml.example` in this repo is the generic template. `auth` currently writes a **single** account (it overwrites `config.toml`). Himalaya itself supports several `[accounts."…"]` blocks if you edit the file by hand.
